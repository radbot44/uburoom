# Upgrading

uburoom uses `/ubu` and `!ubu` exclusively. At startup, the bot replaces this application's command set in its configured guild with `/ubu`; it does not change commands belonging to other applications or publish global commands.

The Firefox extension ID is `uburoom@uburoom.com`. Install it as a new extension and pair it with your installation. Its private authentication callback is derived from that ID. Configure the build for your installation's exact HTTPS origin. There are no previous-name aliases for extension identity, storage, cookies, globals, protocol fields, launchers or logo routes. Browser users must sign in again after the naming transition.

Configuration uses private `config.yaml`; copy the blank example for a new installation. YAML is the sole runtime authority. Until full release, configuration conversions and schema/data changes are handled with reviewed, task-specific one-off scripts outside the shipped application. There is no bundled converter or automatic migration during startup/deployment. Keep private configuration and the original key/state together; never share them. Use `--config <path>` for an external YAML file.

When retaining existing data, keep account UUIDs, linked identities and encrypted records unchanged. Before starting an existing database, copy the exact original 32-byte encryption key into the runtime user's `LOCALAPPDATA/uburoom/credentials.key` (Linux: `$XDG_DATA_HOME/uburoom/credentials.key`, normally `~/.local/share/uburoom/credentials.key`; macOS: `~/Library/Application Support/uburoom/credentials.key`), or set `storage.credential_key_file` to its private absolute path outside the project. Never generate a replacement key for existing accounts. Back up the matched database/state and key before upgrading; startup refuses an existing database with a missing key.

Use only the uburoom launchers. Select a tested revision, install dependencies on the runtime machine and restart during an agreed maintenance window. Keep private state outside Git and preserve it when replacing code. See self-hosting.md for backups/deployment and testing.md for pending live verification.

**First-release storage baseline:** Schema version 6 includes users, identities, encrypted credentials, metadata, audit, devices, browser logins, playback history and the M1-P13 room/host/queue tables, including auto-queue cycle state, autoplay, room lifetime/capacity, restart recovery, compact completion progress, first-sign-in markers and pending provider-bound host grants. Startup creates it only for an empty database. A complete version-6 database reopens without changing UUIDs or encrypted values. Private version-1 through version-5 databases are rejected unchanged: no automatic upgrade/reset or room-table installation occurs. An absent database alongside legacy JSON, incomplete/unversioned layouts and newer schemas also fail explicitly. Review a matched backup and manual state transfer before attaching retained private state to this baseline. Published releases must add explicit forward migrations when a supported baseline changes.

**Private pre-release transfer procedure:** Before deployment, stop the existing process and take a restricted, matched offline copy of the database, exact original key, private configuration and TLS files. Check SQLite integrity and verify copied hashes. Keep old JSON files as private historical inputs; they are never read or rewritten by the runtime. Verify a copy of the database against the baseline and restore that copy with its original key in isolation. If startup rejects its layout, leave production stopped on that attempted revision and retain the untouched backup: choose either a reviewed manual transfer preserving UUIDs, identity links and ciphertext, or an explicitly approved reset. Do not delete state or replace a key to make startup pass. Code rollback alone does not restore a matched state backup. The automated offline-copy fixture verifies the baseline restore; it does not authorize or perform an operator transfer.

Runtime writes are serialized by a worker into this one database. HTTP completions and WebSocket request acknowledgements await committed writes; shutdown flushes outstanding work. An abrupt process loss can discard observations not yet acknowledged. A storage failure is reported and prevents successful durability acknowledgements. Stop the server before an ordinary file-copy backup, or use SQLite's online backup; copying the file during a transaction is unsafe. Rolling back across private pre-release storage layouts requires the corresponding matched offline backup and can lose later changes, including sign-outs and revocations; this path will not be supported by the initial public release.

Reload open watch pages after upgrading to watch protocol 18, and reinstall the matching configured Firefox extension. This intentionally breaks private pre-release clients. Allow WebSocket upgrades for `/watch-socket` and `/ws` through the HTTPS proxy. Room preparation, commands, readiness, observations, listing and lifecycle operations use authenticated WebSocket messages; their old HTTP routes return 404. Authentication/account bootstrap, catalog, artwork, media, playback history and health remain HTTP resources. There is no HTTP room-polling fallback. The engine and extension use only `room.*`, `roomId`, `room` registration and `room-ack`; `session.*`, `/api/sessions` and legacy room IDs are unsupported. A socket disconnect revokes consent and ends that viewer's stream; a same-tab rejoin within the process-local grace obtains fresh playback authority and retains personal track choices. A daemon restart clears rooms and consent.


The room lifecycle update uses configuration schema v2c. Add the new `rooms` limits from the example and remove the retired `rooms.single_room_name`; single-room mode always uses **Room**. Retained private version-4 state requires an explicit reviewed offline transfer with the original credential key and a verified restricted backup. Existing rooms should retain Keep room when empty and start a fresh inactivity period because older last-access times are unavailable. Run the transfer/configuration helper a second time to verify no changes. Neither startup nor deployment performs this transfer automatically. Review the selected code/configuration together before restarting.

The account-name/directory update uses configuration schema v2d and SQLite baseline 6. Directory exposure defaults are Discord on and Plex off. A reviewed offline transfer of retained version-5 state must preserve UUIDs, current names, explicit hosts and exact credential-key bytes. Existing verified accounts receive an unknown historical sign-in marker rather than an invented timestamp. All hosts and delegated Add hosts remain off in old saved policies. Verify transfer/configuration idempotence before restarting. Provider setup and real-provider checks are separate from the transfer.
