# Upgrading

uburoom uses `/ubu` and `!ubu` exclusively. At startup, the bot replaces this application's command set in its configured guild with `/ubu`; it does not change commands belonging to other applications or publish global commands.

The Firefox extension ID is `uburoom@uburoom.com`. Install it as a new extension and pair it with your installation. Its private authentication callback is derived from that ID. Configure the build for your installation's exact HTTPS origin. There are no previous-name aliases for extension identity, storage, cookies, globals, protocol fields, launchers or logo routes. Browser users must sign in again after the naming transition.

When retaining existing data, keep account UUIDs, linked identities and encrypted records unchanged. Before starting an existing database, copy the exact original 32-byte encryption key into the runtime user's `LOCALAPPDATA/uburoom/credentials.key` (or the equivalent home directory on other platforms), or set `UBUROOM_CREDENTIAL_KEY_FILE` to its private absolute path outside the project. Never generate a replacement key for existing accounts. Back up the matched database/state and key before upgrading; startup refuses an existing database with a missing key.

Use only the uburoom launchers. Select a tested revision, install dependencies on the runtime machine and restart during an agreed maintenance window. Keep private state outside Git and preserve it when replacing code. See self-hosting.md for backups/deployment and testing.md for pending live verification.

**Current private pre-release builds:** M1-P11 introduced schema version 1 and a one-time import from `data/devices.json` and `data/logins.json`. Import markers prevent stale files from restoring revoked credentials; those JSON files are no longer updated. This describes the current implementation, **not** a migration promise for the first public release.

**Final M1 first-release preparation:** Remove the old JSON import, import markers and migrations between unpublished pre-release SQLite layouts, then test a fresh database and a matched backup/restore on the supported baseline. There is only one pre-release operator; handle that installation by an explicit private backup plus chosen reset or reviewed manual transfer. Never silently overwrite its accounts, lose linked identities or regenerate a key for an existing encrypted database. Public releases must establish a supported schema baseline and forward migration/rollback policy for future user upgrades.

Runtime writes are serialized by a worker into this one database. HTTP completions and WebSocket request acknowledgements await committed writes; shutdown flushes outstanding work. An abrupt process loss can discard observations not yet acknowledged. A storage failure is reported and prevents successful durability acknowledgements. Stop the server before an ordinary file-copy backup, or use SQLite's online backup; copying the file during a transaction is unsafe. Rolling back across private pre-release storage layouts requires the corresponding matched offline backup and can lose later changes, including sign-outs and revocations; this path will not be supported by the initial public release.

Reload open watch pages after upgrading to watch protocol 16. Allow WebSocket upgrades for `/watch-socket` through the installation's HTTPS proxy, as well as `/ws` for the Firefox remote. Authentication/account bootstrap and media remain HTTP. There is no HTTP room-polling fallback. M1-P11 will also remove obsolete HTTP **room-control** compatibility routes after moving shared operations out of the current HTTP-shaped WebSocket adapter; clients should use authenticated WebSocket room messages. The first public release will not support legacy `session.*` commands or `/api/sessions`. A socket disconnect revokes consent and ends that viewer's stream; a same-tab rejoin within the process-local grace obtains fresh playback authority and retains personal track choices. A daemon restart clears rooms and consent.
