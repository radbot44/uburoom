# Plex activity, watch state and per-viewer reporting — investigation

Updated: 2026-10-20. **No product reporting implementation.** Initial research used a supplied source archive and isolated fixtures. Authorized live Original-mode probes verified personal activity/resume side effects and subsequently found a bounded activity-only request shape; see [watch-state separation](#activity-only-reporting-and-personal-state-separation). The later [HLS/AV1 follow-up](#hls-and-av1-separation-follow-up-2026-10-20) extends bounded separation evidence and records delivery-classification and AV1-ending gaps. The [association investigation](#plex-delivery-association-investigation-2026-10-20) resolves isolated HLS classification; shared-producer stop behavior and external AV1 telemetry remain unresolved. Supports M1-P4, the M1-P14 media-entitlement boundary, and the later M2-P3 guest-pass model. Preserve Discord login and the existing authorized Discord Activity **Open in web app** flow.

## Decision in brief

1. **Keep three independent outcomes.** (A) Plex server *Now Playing* / dashboard / third-party monitoring visibility, (B) an actual Plex account's resume offset, played flag, and play history, and (C) uburoom's authenticated viewer observations, playback intervals and history. None proves either of the others. In particular, a 200 from `/:/timeline`, a transcode, and an HLS segment fetch are **not** evidence of a per-person Plex dashboard session or of correct Plex history. [P1–P4, C5]
2. **Personal playback:** use only the viewer's currently verified Plex subject and authorized token for any future Plex timeline reporter. One reporter/playback lifetime per actual client; per-viewer observations—not the room clock, HTTP proxy, or encoder—drive its state. The later [separation experiment](#activity-only-reporting-and-personal-state-separation) supports distinct activity reporting and personal-state sync preferences on the tested PMS/Original path and subsequent HLS/AV1 probes; delivery association, AV1 ending and broader compatibility must be verified before shipping. [P2, P4, C1, C5]
3. **Sponsored playback:** admission, source authorization, upstream transport and reporting are *different* authorities. Discord-only viewers and guests get their own uburoom identity/history, but do not thereby acquire a Plex identity. The safest initial sponsored choice is **local per-viewer reporting only** with Plex dashboard attribution shown as *not verified / unavailable*. A separately authorized restricted Plex source account is a possible transport identity, **not** per-guest reporting; test its side effects before offering an opt-in source-activity mode. Never substitute the owner's account. [C1–C4, P1, P5]
4. **Security prerequisite (confirmed defect):** `hub.plexFor()` returns the `PLEX_TOKEN`-backed owner Plex context when no Plex identity or saved credential exists, including when a restricted account's connection has been removed. Discord-eligible admission therefore expands to owner media access. **Block this implicit fallback before any sponsorship feature, including guests.** This is not an approved sponsorship model. [C1]

### What source transport currently does — not to be confused with playback reporting

- **Original:** `Plex.prepare` uses a part URL with no transcode session; `watch-http.stream` proxies authenticated ranged GETs with the viewer's Plex context. Request count, amount fetched and cache activity do not tell whether a frame decoded or the tab was playing. `X-Plex-Client-Identifier` generally comes from stored Plex PIN client ID for scoped sources. [C1–C3]
- **Plex HLS:** forced H.264/AAC decisions and `start.m3u8` use a fresh `transcodeId`. A pool group is keyed by room/media/source/quality/audio/burn; the *producer's* scoped credential starts it. Each consumer has its **own** `media.plexContext`, authorized 15-second media grant, caption settings and local observations; manifest/segments can instead be fetched through `hlsContext` (the producer). Reusing a transcode is neither impersonation permission nor an independent Plex watch session. Producer loss/last-lease stop affects encoder lifetime, not necessarily other consumers' playback. [C2–C3]
- **uburoom AV1:** an uburoom-managed `ffmpeg` job encodes from Plex's original part through a private loopback bridge. The chunk pool deduplicates identical output; `lease.source` is separate but a shared cached chunk was encoded only once. There is **no** PMS HLS transcode ID for these viewers and no Plex timeline API usage. More than one Plex source identity can share AV1 chunk output under the room/share key. [C3]
- **Important existing side effect:** HLS preparation sometimes sends **`PUT /library/parts/{partId}?audioStreamID=...`** and **`PUT ...?subtitleStreamID=...`**, then attempts to restore the prior selection. These are **real Plex preference writes**, even when watch-state reporting is disabled. They can race with native Plex apps despite the local part lock; exceptions/failed restore can leave changed preferences. These are not progress/scrobble writes, and belong in the side-effect disclosure and consenting live-test review. [C3]
- No code here invokes `/:/timeline`, `/:/progress`, `/:/scrobble` or `/:/unscrobble`. `ping`/`stop` refer to PMS transcoder lifecycle, **not** a playback timeline. Local observations write the uburoom SQLite `playback_history` table instead. [C3–C5]

### What the local evidence actually proves

The browser emits observations on player events and approximately every second, derived from `video.currentTime`, the video state, `observationFrames`, monotonic sequence and server-estimated timestamps. The server verifies the *current authenticated actor*, `viewerId`, room access, media/stream/observation epochs, monotonic sample and timing. Credit requires consecutive decoded/advancing `playing` samples: it excludes buffering, paused state, seeks, replays, missing frames, large timing gaps and clock jumps. Events/state still persist even without credited watch seconds. `playback_history` stores provenance (identities *at creation*, not a retroactive account rewrite), room, delivery, positions/states, intervals, end reason; after a crash incomplete entries become `interrupted`. It retains at most 90 days / 5,000 records and exposes up to 100 detailed records via the authenticated `/api/watch/playback`. Across a canonical account, totals union overlapping wall/source intervals; overlapping tabs remain separate detailed records. [C5]

**Limits:** client data is validated but not cryptographic proof of a human watching; decoded frames are a stronger signal than server intent, not absolute truth. The server cannot extrapolate a stopped last frame after heartbeat loss. A new stream/observation epoch can produce a new local record for the same real-world viewing occurrence; queue history is separate and should not be mistaken for personal watches. `mediaId` is an item rating key under the configured machine; a future multi-PMS implementation must include server identity in local aggregation keys. Current `sessions` terminology in `/api/watch/playback` is a technical local history shape, not Plex session IDs. [C5]

## Architectural decisions recommended for a later implementation

### Personal mode: real viewer reporting, not encoder reporting

- Gate on **current** verified `plex` subject, exact pinned PMS machine, item visibility/entitlement, token validation and opt-in; make no report if any are absent or revoked. Resolve source transport and optional personal reporting authorization separately; never let the source-token fallback satisfy reporter entitlement. The Plex `User` shown is expected to follow the token's authenticated Plex subject [P2], **subject to PMS read-back tests**. Product/device names only label clients.
- Define an immutable **report occurrence**: canonical uburoom account ID + proven Plex subject + pinned machine + Plex item/edition/source + room media occurrence + per-tab/device lifetime. Mint a distinct, stable `X-Plex-Client-Identifier` per installed browser client (not per transcode and not a fake user), and a distinct `X-Plex-Session-Identifier` **per playback**, persisting it across short same-tab reconnect only if the same identity/item/occurrence and fencing generation truly remain active. Store no token in the browser or logs.
- Use validated actual viewer observations (`playing`, `paused`, `buffering`, `seeking`, `ended`, stop/disconnect) as reporter input. Map `seeking` to a documented PMS state (usually buffering/paused as observed), never invent a `seeking` Plex enum. Clamp position to known duration; preserve actual measured position during pause/buffer, not the advancing room clock. Batch at documented cadence and state transitions *after* confirmation; serialize per occurrence; prohibit state rewinds across out-of-order responses.
- Add durable per-occurrence reporter ledger (token subject *identifier*, session ID, ack/error/lease/sequence/fencing status, never plaintext token) **only when implementation is authorized**. Recheck policy and token before dispatch and after awaits; block stale mediaVersion/streamVersion/observationEpoch, duplicated sequence, logout/unlink/revocation and stale handoff completions. Final `stopped` should be bounded best effort, not an assumption when a process crashes; never backfill old or disconnected progress using extrapolation.
- **Plex resume conflict rule:** several tabs and external Plex apps share a user's account watched state. Local precedence may choose a *single* reporter for one `(PMS, Plex subject, ratingKey)` when conflicts exist, with an explicit UI state for suppressed concurrent sessions. A separate Plex app cannot reliably be fenced by uburoom alone; do not promise no resume clobbering. If reliable last-writer/collision semantics are unverified, default to `local only` / disable personal Plex writes on conflict, not a blind progress retry. Never call scrobble merely to manufacture history or dashboard activity.
- Use read-only reconciliation (`GET /status/sessions`, `GET /status/sessions/history/all`, read-only per-user item metadata including `viewOffset`, `viewCount`, `lastViewedAt` where returned) to confirm outcomes, subject to permissions and Plex Pass limitations. Require actual observed same-person PMS user/player/playback identity, not just matching item IDs. Expose independent booleans `plexNowPlayingObserved` and `plexWatchStateVerified`; `requestAccepted` is merely transport acknowledgement. No silent optimistic `reported to Plex` label.

### Sponsored mode: restricted source, separate viewers

- Add an explicit operator-approved `sponsoredMediaGrant` policy **later**, binding sponsor source *identity* and credential, exact machine, allowed libraries and/or items, room/occurrence, allowed audience (Discord role/account or guest-pass), concurrency/bitrate caps, expiry and revoke version. Enforce for catalogs/search, metadata, artwork, captions, source selection, each HLS/AV1 segment and stream refresh; source changes or grant revocation invalidate existing grants/sockets/output leases. Any requested item must satisfy both source credential's *actual* PMS entitlement and the local grant ceiling. Do not leak operator credential to clients or permit unrestricted browsing. A login/admission grant alone never selects owner Plex access.
- **Default option:** `sponsored: local per-viewer only`. Independently show live uburoom view status and playback history under actual Discord/guest UUID; show *Plex attribution: shared source / per-guest Plex activity unavailable*. Do not dispatch sponsored timeline/scrobble/progress calls. Existing upstream transfer/conversion might still be logged in Plex, and selection `PUT`s may occur; neither is a per-person Plex dashboard assertion.
- **Optional conditional option (NOT approved):** a dedicated *real, separately authenticated* Plex source identity with restrictive server-library access. It could confine unavoidable reporting-state changes to that identity if the server allows its token to serve the selected media, and potentially show it as one Plex account on the dashboard; separate device labels might help trace activity but **never create distinct guest users**. A managed Plex Home user is not guaranteed to support the current full-account PIN/resource-token flow [P5]; test a standard separately authorized account first. One shared sponsor identity accumulates one watch state/competing resumes across guests. The server owner stays separate and is never the implicit sponsor. Verify both technical limits and Plex account/sharing rules with the operator before enabling such a model.
- Do not offer a `dashboard only, no watch-state effects` toggle based solely on request flags or a 200. The documented Plex timeline protocol does not establish a read-only activity registration mode [P2]. If controlled evidence shows the server links a visible session to progress/history mutation, disclose it or prefer no Plex reporting for sponsored viewers. **Read-only inspection cannot create a Now Playing entry.**
- Guest-pass issuer and room host authority must not confer Plex credentials, server administration or unlimited sponsorship; default guests denied until both admission and *explicit media sponsorship* are valid. Guest display names are unverified. Conversion to a proved account never retroactively upgrades guest events to that Plex person's history without a separate opt-in transfer rule.

## Authorization and admin-panel consequences (M1-P14; prerequisites for M2-P3)

**Server policy must exist before UI.** First replace `hub.plexFor`'s missing/unlinked credential `return plex` with an explicit deny or exact grant-resolution contract; test stored-but-invalid token, removed connection, Discord-only eligible member, every delivery/cached path and continued Activity handoff. Deny precedence after account merge, logout, role loss, guest-pass revocation and server media changes. Treat the configured owner token as a private **maintenance/source-capability credential**, not implicit permission for every account. The `principal==='discord-shared'` shortcut in `watch-operations.js` (item visibility) and all catalog/queue/image/track/AV1 access checks must go through the same policy; hiding catalog controls does not stop direct media URLs. A 30-second Plex scope cache and a 15-second media grant are current implementation details, **not** a complete revocation SLA. [C1–C3]

### Product implications

- Plan a user preference **Update my Plex progress and watched status** independently of operator-controlled Plex activity reporting. On the verified path, enabled supplies the true `duration`; disabled omits it on **every** timeline state, including buffering, pause, replacement, stop and ending, while preserving correct user/item/position. Avoid any automatic `/:/progress` or scrobble path when personal sync is disabled.
- Serialize reports and fence their policy version. Apply opt-out only after already-dispatched full-sync requests settle; do not acknowledge it and then allow an old queued report to mutate state. Verify restart, quality changes, multiple tabs and Activity/browser handoff preserve the preference.
- Verify per-PMS-version and per-delivery-path compatibility. If activity-only support cannot be established, do not silently substitute full personal synchronization for an opted-out user. Surface the limitation explicitly and select the reporting behavior according to the resolved operator/user policy.
- This supplies a viable design direction for a **verified Plex account**. It does not create a Plex identity or entitlement for a Discord-only viewer or guest. Their sponsored-source attribution remains a separate unresolved contract.

## Plex delivery association investigation (2026-10-20)

The operator prioritized resolving Direct Play classification before investigating AV1 ending. Additional consenting live tests used the same isolated Plex account, movie and PMS version; personal synchronization stayed disabled for every timeline state. No application implementation, production restart/configuration or AV1-ending change was made.

### HLS: real transcode association verified

The missing link was the **Plex playback-session identifier**. Matching a timeline report to the playback session used during Plex's decision/start requests attached the actual `Session`, `TranscodeSession` and selected output `Media` to the viewer's activity entry. Plex/Tautulli then showed hardware H.264 transcoding, AAC direct stream, MPEG-TS/HLS, actual 720×404 output and approximately 1.5 Mbps session bandwidth, rather than original MP4/H.264 4K Direct Play. The selected preset was a 2 Mbps ceiling, not a promise that Plex would encode 1280×720 or consume exactly 2 Mbps.

A fresh approximately 50-second confirmation omitted `hasMDE` as well as duration and still attached the correct HLS output. The final approximately 40-second confirmation followed the structure observed in first-party Plex Web, keeping **all three identifiers distinct**:

| Identifier | Role and verified use |
| --- | --- |
| `X-Plex-Client-Identifier` | Identifies the actual viewer client. Kept consistent across preparation and timeline reporting; the activity Player retained this exact client identity. |
| `X-Plex-Session-Identifier` | Identifies the playback occurrence. Kept consistent across decision/start and timeline requests; the activity Session ID matched it. |
| Universal-transcode `session` parameter | Identifies the encoder job. The activity TranscodeSession key matched this different job ID. |

The existing uburoom preparation path currently uses the transcode ID for both client and session identifiers; the isolated final probe changed only its request wrapper to supply the distinct identities. Product code remains unchanged. Merely adding `hasMDE=1` to an otherwise unrelated timeline client did not attach the stream. The initial multi-phase experiment found the successful session link, but its linked stopped report then terminated the job; later phases after that point are **not valid independent evidence** against other identifier combinations.

Every tested watch/track read-back remained at the existing baseline: resume 601.855s, view count 0, last-viewed unchanged, selected audio unchanged and no matching personal history row. Correct Plex account/movie/position and decoded playback were verified; owner metadata remained unchanged. This extends the activity-only candidate to truthful **individual Plex HLS stream** reporting on the tested installation.

### Shared producer boundary: stopping is consequential

A stopped timeline report with the matching playback-session link caused PMS itself to terminate the associated transcode. Client-specific PMS logs recorded termination with reason `Client stopped playback`; subsequent pings returned 404. The test helper had not yet called the universal-transcode stop endpoint at that point. Therefore a viewer's linked stopped report must not be treated as a harmless way to clear only that viewer's dashboard entry when a producer serves others.

A fresh test tried sending stopped under the same client but an unrelated playback-session identifier. The transcode survived, **but the original linked activity entry remained playing**. This is a failed workaround, not a safe detach operation. It required an exact test-user/client/item/session-matched stopped cleanup, which cleared the stale entry; personal state stayed unchanged. A subsequent setup was refused because that stale test entry was still present; it produced no decoded playback. Its idle helper was stopped before retry, and the overlap preflight was moved ahead of helper launch.

The supported design direction is separate viewer-client, playback-occurrence and producer-job identities. Before pooled reporting, determine whether PMS can maintain distinct per-viewer playback resources referencing one authorized job, including leave, pause, replacement and last-viewer cleanup, without collapsing accounts or letting one viewer stop everyone. No multi-account/shared-producer support is established by these single-viewer tests. Do not fix this by leaving stale playing entries, impersonating the owner, or marking shared producer progress as independent viewer evidence.

### External AV1: timeline output fields did not change PMS classification

An actual approximately 50-second uburoom AV1/Opus WebM run supplied truthful output fields on timeline reports (`videoCodec`, `audioCodec`, `container`, `protocol`, `videoDecision`, `audioDecision` and decoded width/height), with `hasMDE=1` and no duration. PMS accepted the requests but ignored those output declarations for activity: it continued returning the original MP4/H.264 4K media without an attached TranscodeSession. User/movie/position remained correct and saved watch state stayed unchanged.

Uburoom's AV1 encoder runs outside PMS and reads the original source file. Unlike HLS, it has no PMS-owned encoder job to attach. The [documented timeline API](https://developer.plex.tv/pms/) does not define these output declarations as an external-encoder registration contract. Read-only inspection of the first-party Plex Web decision/timeline builders and [Plex for Kodi reporting](https://github.com/plexinc/plex-for-kodi/blob/master/lib/_included_packages/plexnet/nowplayingmanager.py) did not establish a supported registration mechanism. **No supported way to make PMS represent this external AV1 job was found; this is not proof that every undocumented mechanism is impossible.**

Keep accurate account/movie/time activity in Plex and distinguish Plex's original-source transfer from the downstream AV1 delivery in uburoom's telemetry. If full native Plex transcode telemetry is required, use a delivery job actually managed by PMS. Do not create an unused shadow transcode, substitute a fake job ID or send invented stream details to make the card say Transcode. A descriptive player label could explain external delivery but would not repair PMS codec, bandwidth or encoder accounting; any naming change remains a product decision.

The classification investigation therefore resolves isolated Plex HLS attribution while identifying two explicit remaining boundaries: shared-producer lifecycle and external AV1 telemetry. AV1 stalling remains deferred as requested. All live helpers/forwards and test encoders were stopped, stale test activity was cleared and intentional preexisting test progress was retained. Raw source/request/read-back/log/screenshot evidence stays private; product reporting remains unimplemented.
